## Storage Stack คืออะไร

ลองนึกภาพตอนที่เรารันคำสั่ง `cat abc.txt` เพื่ออ่านไฟล์ โปรแกรม cat ก็จะต้องไปดึงเนื้อหาไฟล์ abc.txt จากใน drive ออกมาใช่ไหมครับ ซึ่งเบื้องหลังก็จะมี 
component มากมายทั้ง hardware และ software มาทำงานร่วมกันเพื่อดึงเนื้อหาไฟล์ abc.txt ออกมาตามที่โปรแกรม cat ต้องการ

Storage stack เป็นเหมือนคอนเซปต์ที่แบ่งกลุ่ม component เหล่านี้ออกเป็นส่วน ๆ ตามขอบเขตหน้าที่ แล้วนำเรียงซ้อนต่อกันเป็นชั้น (stack) ซึ่งแต่ละชั้นก็จะมีขอบเขตหน้าที่แตกต่างกัน 
ทำงานกันคนละส่วน รวมถึงมีข้อกำหนดหรือมาตรฐานที่แตกต่างกันด้วย แต่ชั้นที่อยู่ติดกันก็จะทำงานร่วมกัน และข้อมูลก็จะวิ่งจากชั้นหนึ่งไปอีกชั้นหนึ่งที่อยู่ติดกัน ถ้าใครรู้จัก OSI model ตัว 
storage stack ก็จะคล้าย ๆ กันครับ แต่ OSI model จะเป็น network ส่วน storage stack เป็น storage แทน

Storage stack จะแบ่งออกคร่าว ๆ ได้เป็น 6<sup>**\***</sup> ชั้น ตามแผนภาพด้านล่างครับ โดยจะเริ่มต้นที่ User Applications ไปจบที่ Hardware หรือก็คือตัว physical drive นั่นเอง

<Note>
จริง ๆ แล้วจำนวนชั้นของ storage stack เนี่ยผมก็ฟันธงตัวเลขที่แน่นอนไม่ได้เหมือนกัน บางเจ้าก็จะบอกว่ามี 5 ชั้น บางเจ้าก็ว่า 7 ชั้น 
ซึ่งจริง ๆ แล้วมันก็คือการรวมหรือแยกบาง layer ออกจากกัน แต่การแบ่งเป็น 6 ชั้นตามบทความนี้ส่วนตัวผมมองว่าเมคเซนส์ที่สุด แถมอธิบายง่ายด้วย ผมก็เลยจะถือว่ามันมี 6 ชั้นไปละกันนะครับ
</Note>

## สำรวจ Storage Stack

จากภาพด้านบน ทีนี้เราจะมาลงรายละเอียดของ stack แต่ละชั้นกันครับ

### 1. User Applications

เริ่มกันที่ชั้นแรกซึ่งเป็นชั้นที่เข้าใจง่ายที่สุดกันก่อนเลย user applications ก็คือพวกแอปที่ user อย่างเรา ๆ เรียกใช้ครับ ไม่ว่าจะเป็นคำสั่งใน Linux อย่าง cat, cp, ฯลฯ หรือโปรแกรมที่เรา ๆ 
คุ้นเคยกันดีอย่าง Microsoft Word, PowerPoint เป็นต้น ว่าง่าย ๆ ก็คือเป็นชั้นของ user ที่เรียกใช้โปรแกรมเพื่อเข้าถึงข้อมูลไฟล์ต่าง ๆ ที่อยู่ใน drive ครับ

ยกตัวอย่างต่อจากตอนเริ่มบทความเลย คือพอเรารันคำสั่ง `cat abc.txt` สิ่งที่โปรแกรม cat ทำก็คือมันจะไปเรียก **system call** ของ OS เพื่อขอข้อมูลไฟล์ abc.txt ออกมา ซึ่งจริง ๆ แล้วตัว
OS เองจะมี component ภายในหลาย ๆ อย่างไว้คอยจัดการกับ system call ที่แตกต่างกัน และสำหรับ component ที่รับหน้าที่จัดการคำขอ system call ที่เกี่ยวข้องกับการจัดการไฟล์ เช่น 
open(), read(), close() คือ component ที่เรียกว่า **Virtual File System (VFS)** หรือก็คือ layer ชั้นที่ 2 ที่เรากำลังจะพูดถึงต่อไปครับ

### 2. Virtual File System (VFS)

ตั้งแต่ชั้นนี้ลงไปเราจะเริ่มเข้าสู่ kernel space แล้วครับ เพราะหลังจากนี้ทุกอย่างจะถูกจัดการโดย OS ทั้งหมด

สำหรับชั้นนี้ก่อนจะรู้จักกับ virtual file system ผมขอพูดถึง file system ก่อนละกันครับ

#### File System

ลองนึกภาพว่าเรามีโกดังโล่ง ๆ ซักแห่งหนึ่ง แล้วเราก็มีกล่องลังที่บรรจุของอยู่เต็มไปหมดซึ่งเราอยากจะเอากล่องลังเหล่านี้เข้าไปเก็บไว้ในโกดัง ทุกคนคิดว่าเราควรจะจัดเรียงกล่องลังเหล่านี้แบบไหนดี?
คำตอบก็คือ "ไม่รู้ครับ 555" เพราะจริง ๆ แล้ววิธีการจัดเรียงกล่องลังเข้าไปในโกดังนั้นสามารถทำได้หลายวิธีมาก และแต่ละวิธีก็อาจจะมีข้อดีข้อเสียต่างกัน เช่น บางวิธีอาจจะทำให้เราสามารถเก็บกล่องลังได้เยอะแต่ลำบากตอนหา
บางวิธีอาจทำให้สามารถหากล่องลังที่ต้องการได้ง่ายแต่ก็จะเก็บได้น้อยกว่า, ฯลฯ วิธีที่เหมาะสมที่สุดจึงขึ้นอยู่กับว่าเป้าหมายของเราคืออะไรครับ

ทีนี้ลองนึกภาพว่าเราซื้อ SSD มาอันนึงครับ เป็น SSD เปล่า ๆ เลย แล้วเอาไปใส่เครื่องคอมพิวเตอร์ คอมพิวเตอร์ก็จะเอาข้อมูลมาเก็บไว้ใน SSD อันนี้ใช่มั้ยครับ คำถามคือ แล้วเครื่องคอมพิวเตอร์ควรจะเก็บข้อมูลแบบไหนถึงจะดีที่สุดล่ะ?
ปัญหาเดียวกับเรื่องโกดังเมื่อกี้เลยครับ โดยที่ SSD คือโกดัง และข้อมูลคือกล่องลัง และเนื่องจากวิธีการเอาข้อมูลไปเก็บใน SSD มันสามารถทำได้หลายวิธีมาก ถ้าพูดเปรียบเทียบแบบห่วย ๆ เลย เราเรียกแต่ละวิธีว่า **file system** ครับ

File system เป็นเหมือนวิธีการจัดเก็บข้อมูลลงในไดรฟ์ เช่น ก่อนเก็บจะแบ่งข้อมูลเป็นส่วน ๆ ไหม ถ้าแบ่งจะแบ่งยังไง แล้วข้อมูลที่แบ่งส่วนแล้วจะเอาไปเรียงกันแบบไหน จะใช้วิธีไหนไหนการค้นหาข้อมูลออกมา เป็นต้นครับ 
เราทุกคนสามารถสร้าง file system ของตัวเองขึ้นมาได้นะครับถ้าเราคิดว่าวิธีเก็บไฟล์ของเราเจ๋งพอ (แต่ผมไม่ทำละคนนึง) หรือเราจะใช้ file system ที่คนเก่งคนอื่น ๆ เขาออกแบบไว้ก็ได้ โดย file system 
ที่ได้รับการยอมรับและเป็นที่นิยมใช้กันก็มีหลายตัว อย่างเช่น EXT4, NTFS, ATFS, FAT32 เป็นต้น โดยแต่ละตัวก็จะออกแบบมาให้มีข้อดีข้อเสียแตกต่างกันไป เหมาะกับ use case คนละแบบครับ

ไหน ๆ ก็พูดถึง file system แล้ว ผมขอแนะนำ file system ยอดนิยมแบบคร่าว ๆ ซักหน่อยละกัน

| ----------- | ----------- | :------------------------------------------------------------------------------------------------------------------- |
| NTFS        | Windows     | Microsoft สร้างมาไว้สำหรับใช้กับ Windows โดยเฉพาะ ใช้ข้าม platform ไม่ได้ (MacOS สามารถอ่าน NTFS ได้ แต่เขียนไม่ได้) |
| APFS        | MacOS / iOS | Apple สร้างมาไว้สำหรับใช้กับอุปกรณ์ใน ecosystem ของ Apple โดยเฉพาะ ใช้ข้าม platform ไม่ได้ |
| EXT4        | Linux       | file system ยอดนิยมของ Linux เร็ว แรง เสถียร แต่ใช้ได้แค่กับ Linux อย่างเดียว |
| FAT32       | Universal   | file system ที่เป็นพ่อทุกสถาบันเพราะใช้ได้กับแทบทุกอย่าง Mac, Windows, Linux, ทีวี, ตู้เย็น, หรืออะไรก็ได้ที่มีช่องเสียบ USB (flash drive ก็ใช้ FAT32) เสียอย่างคือใช้กับ partition ที่ขนาดเกิน 32GB ไม่ได้ |

| ZFS         | Linux       | file system ที่มีความสามารถ self-healing สามารถซ่อมไฟล์ที่เสียได้ จุดขายคือการันตีว่าข้อมูลที่บันทึกไว้จะไม่มีทางเสียหาย แลกมากับความช้า การจัดการที่ยุ่งยากและกิน RAM ชนิดที่ Google Chrome เรียกพี่ ไม่เหมาะกับคอมบ้านด้วยประการทั้งปวง |

เพิ่มเติมอีกนิด คือโดยปกติแล้วเวลาเราซื้อไดรฟ์ (เช่น SSD) ใหม่มาที่เป็นไดรฟ์เปล่า ๆ เลยเนี่ย ตัวไดรฟ์มันจะยังใช้ไม่ได้นะครับ เราจะต้องทำ 2 อย่างก่อน ก็คือ partition กับ format

##### **Partition**

การทำ partition คือการแบ่งไดรฟ์ออกเป็นส่วน ๆ แล้วเวลาเราเอาไดรฟ์ไปต่อเข้ากับเครื่องคอมพิวเตอร์ ตัว OS มันจะตีความว่าเรามีจำนวนไดรฟ์เท่ากับจำนวน partition ในไดรฟ์นั้น เช่น ถ้าเรามีไดรฟ์ขนาด 1TB 
ทำการแบ่ง partition ออกเป็น 2 partition ขนาด 500GB เท่ากัน OS ก็จะตีความว่าตอนนี้เครื่องคอมพิวเตอร์มีไดรฟ์ขนาด 500GB 2 ลูกเชื่อมต่ออยู่

ซึ่งพอเราทำ partition แล้ว ตัวไดรฟ์จะทำการบันทึกข้อมูล partition เอาไว้ใน**ตาราง partition** ที่อยู่ภายในตัวมันแบบถาวร ทำให้ต่อให้เราถอดเอาไดรฟ์ตัวเดิมไปใส่ที่คอมพิวเตอร์เครื่องไหนก็ตาม 
ไดรฟ์ของเราก็จะถูกตีความเป็นไดรฟ์ขนาด 500GB 2 ลูกเหมือนกันหมดครับ เพราะ OS จะอ่านข้อมูลจากในตาราง partition แล้วตีความออกมา แต่ไม่ต้องห่วงนะครับ เพราะเราสามารถแก้ไขเพิ่ม/ลด partition 
ได้ตลอด ตัว OS ก็จะแค่อัปเดตข้อมูล partition ใหม่ลงในตาราง partition แค่นั้น

แล้วก็ตาราง partition เนี่ยก็มี format ของมันเหมือนกันนะครับ เนื่องจากมันก็มีโอกาสที่ไดรฟ์อันเดียวจะถูกเอาไปต่อเข้ากับอุปกรณ์นู่นนี่ที่เป็นคนละ OS กัน เดี๋ยวก็ Windows เดี๋ยวก็ Linux ถ้าตาราง partition 
มีโครงสร้างแบบตามใจฉันมันจะทำให้ข้อจำกัดในการใช้ไดรฟ์สูงขึ้นมาก โดย format ยอดฮิตจะเรียกว่า GPT ซึ่งทั้ง Windows, Mac, Linux จะใช้ format นี้หมด 
ทำให้เราสามารถซื้อไดรฟ์ตัวเดียวแล้วเอาไปต่อกับอุปกรณ์อะไรก็ได้โดยไม่ต้องแคร์ OS ครับ แต่ถ้าเป็นอุปกรณ์รุ่นเก่า ๆ จะใช้อีก format นึงที่เรียกว่า MBR แทน ส่วนรายละเอียดผมขอไม่ลงเพิ่มแล้วนะครับ 
เดี๋ยวจะไหลยาวเกิน

##### **Format**

การ format เนี่ยพูดง่าย ๆ ก็คือการระบุว่าเราอยากให้ partition หนึ่ง ๆ ในไดรฟ์ใช้ file system อะไร เช่นผมอาจจะมีไดรฟ์ขนาด 1TB ที่แบ่งเป็น 2 partition ขนาด 500GB
ผมก็สามารถ format partition แรกให้ใช้ NTFS แล้วก็ format partition อีกอันที่เหลือให้ใช้ EXT4 ทีนี้ผมก็จะได้ไดรฟ์ที่สามารถใช้ได้กับทั้ง Windows และ Linux แต่แบ่งความจุกันคนละ 500GB

แต่ละ partition เนี่ยจะมีสิ่งที่เรียกว่า **superblock** อยู่ครับ superblock เป็น block แรกสุดของ partition และจะเก็บข้อมูลสำคัญต่าง ๆ ของ partition นั้น ๆ เอาไว้ เช่น partition layout, ขนาด, พื้นที่ว่างที่เหลืออยู่, ฯลฯ
และที่สำคัญคือใน superblock จะเก็บข้อมูลที่เรียกว่า **magic number** เอาไว้ด้วย magic number คือเลขฐาน 16 ที่ใช้ระบุว่า partition นี้ใช้ file system อะไรอยู่ ซึ่ง file system แต่ละประเภทจะมีเลข
magic number เฉพาะเป็นของตัวเอง และ OS จะใช้เลข magic number นี้เพื่อเช็คว่าไดรฟ์ (partition) นี้ใช้ file system อะไร ตอนอ่าน/เขียนไฟล์จะได้ทำงานได้อย่างถูกต้อง หรือถ้าเป็น file system ที่ OS ไม่รองรับก็จะได้ 
handle ได้

เราสามารถลองเข้าไปดู magic number ได้ด้วยนะครับ อย่างในตัวอย่างนี้ก็จะเริ่มจาก

1. ใช้คำสั่ง `lsblk` เพื่อลิสต์ไดรฟ์กับ partition ทั้งหมดออกมาก่อน จะเห็นว่าเรามีไดรฟ์ 1 ลูก (nvme0n1) ที่ข้างในแบ่งออกเป็น 3 partition ซึ่งถ้าดูจากขนาดแล้ว partition nvme0n1p1 ก็น่าจะเป็น partition หลักของเรา
2. ใช้คำสั่ง `blkid /dev/nvme0n1p1` เพื่อดูรายละเอียดของ partition จะเห็นว่า TYPE="xfs" หมายความว่า partition nvme0n1p1 ใช้ file system XFS
3. จากนั้นใช้คำสั่ง `dd if=/dev/nvme0n1p1 bs=1 count=4 | xxd` เพื่ออ่านข้อมูล 4 bytes แรกของ partition ซึ่งเป็นตำแหน่งที่มีข้อมูล magic number เก็บเอาไว้อยู่ 
ค่าที่อ่านได้ก็คือ **00000000: 5846 5342** หรือก็คือ **0x58465342** เลข magic number ของ XFS นั่นเอง

<Note>
file system แต่ละประเภทจะเก็บข้อมูล magic number เอาไว้ในตำแหน่งที่ต่างกัน อย่างเช่นถ้าเป็น EXT4 magic number จะอยู่ที่ตำแหน่ง byte ที่ 1081-1082 ทำให้คำสั่งจะกลายเป็น 
`dd if=/dev/nvme0n1p1 bs=1 skip=1080 count=2 | xxd` แทน
</Note>

จากทั้งหมดที่ว่ามา เราสามารถมองโครงสร้างของไดรฟ์เก็บข้อมูลได้ประมาณนี้ (อันนี้เป็นแค่ภาพรวมคร่าว ๆ นะครับ มีรายละเอียดที่ผมไม่ได้พูดถึงอีกเยอะมากกก ซึ่งมันก็ไปกอง ๆ กันอยู่ใน Others นั่นแหละครับ 
ไหนจะเรื่องลำดับของ block ใน file system อีก ถ้าใครสนใจก็ลองศึกษาเพิ่มเติมดูได้ครับ)

#### Virtual File System

ตอนนี้ทุกคนก็คงจะพอเห็นภาพกันแล้วว่า file system เนี่ยมันมีหลายประเภทมากและแต่ละประเภทก็จะมีโครงสร้างและวิธีการเก็บข้อมูลต่างกัน ทำให้วิธีในอ่านการข้อมูลออกมาก็ต่างกันไปด้วย 
นั่นแปลว่าถ้าคอมพิวเตอร์ของเราจะเข้าไปอ่านไฟล์ abc.txt มันจำเป็นจะต้องรู้ก่อนว่า drive ส่วนที่เก็บไฟล์ abc.txt เนี่ยใช้ file system อะไรอยู่ และหน้าที่ในการระบุ file system 
นี้ก็ตกเป็นของ VFS นี่เอง

ทีนี้ก่อนจะไปต่อเรายังมี component อีกตัวนึงที่ต้องรู้จักก่อนครับนั่นก็คือ **file system driver** ซึ่งเดี๋ยวผมจะเรียกสั้น ๆ ว่า **driver** ละกันครับ หน้าที่ของ driver นี้พูดภาษาบ้าน ๆ ก็คือมันจะเข้าไปเจ๊าะแจ๊ะกับไฟล์ให้เรา
จะบอกว่าเป็นตัวแทนของ file system เลยก็ไม่ผิดนัก เพราะตัว file system เองเป็นเหมือนคอนเซปต์ในหน้ากระดาษว่าจะเก็บหรือจัดการข้อมูลยังไง ส่วน driver เป็นเหมือน implementation ที่ทำงานตามคอนเซปต์ของ 
file system นั้น ๆ ที่วางเอาไว้

โดยทั่วไปแล้ว OS แต่ละเจ้าเขาจะมี driver ของ file system ยอดนิยมหลาย ๆ ตัว (ที่ compatible กับ OS ของตัวเอง) ติดตั้งมาพร้อมใช้งานอยู่แล้ว แต่ถ้าเราอยากใช้งานไดร์ฟที่เป็น file system 
ที่ตัว OS ไม่รองรับ เราสามารถไปโหลด driver ของ file system นั้น ๆ มาติดตั้งเพิ่มเติมได้ เช่น XFS driver พอติดตั้งลงบน Windows ก็จะทำให้เครื่องคอมพิวเตอร์ Windows สามารถทำงานกับ file system XFS ได้
แต่ตอนลง driver ก็ต้องดูรายละเอียดดี ๆ นะครับ เพราะถึงจะเป็น driver สำหรับ file system เดียวกัน แต่ driver ของแต่ละเจ้าก็จะมีฟีเจอร์หรือสิ่งที่ทำได้แตกต่างกันไป เพราะจริง ๆ driver 
พวกนี้ก็ถือเป็น software ชนิดหนึ่งครับ มีคนทำหลายเจ้า บางเจ้าฟรี บางเจ้าเสียตังค์ ก็ต้องดูตรงนี้กันด้วยตอนเลือก driver

กลับมาที่ VFS กันต่อ VFS เป็นเหมือน abstraction layer ที่มาคั่นอยู่ตรงกลางระหว่าง application กับ file system (driver) เพื่อช่วยให้ application สามารถเรียกใช้ไฟล์หรือข้อมูลในไดรฟ์ได้โดยไม่ต้องสนใจว่าไดร์ฟดังกล่าวจะใช้ 
file system อะไร application ก็แค่เรียก system call มาที่ VFS พร้อมระบุชื่อไฟล์ที่ต้องการ (รวมถึง parameter อื่น ๆ ที่จำเป็น) แล้วเดี๋ยว VFS จะรับเรื่องแล้วส่งเรื่องต่อไปให้ driver ที่ถูกต้องเอง

เรื่องรายละเอียดที่ว่า VFS ระบุ file system ได้ยังไงเนี่ยผมขอไม่ลงรายละเอียดนะครับ แต่ถ้าอธิบายคร่าว ๆ ก็คือ VFS จะเอา path ของไฟล์ไปเทียบกับ mount point ทั้งหมดของระบบ (mount table) เพื่อดูว่าไฟล์อยู่ในไดรฟ์หรือ 
partition ไหน แล้วถ้าไดรฟ์หรือ partition นั้นใช้ file system อะไร ก็จะไปเรียก driver ของ file system นั้นครับ 

<Note>
VFS ไม่ได้ทำแบบนี้ทุกรอบนะครับ แต่มันจะมีสิ่งที่เรียกว่า **Dentry (Directory Entry)** เป็นเหมือน cache ที่เก็บข้อมูล mapping ระหว่าง file path กับ VFS inode (struct inode)
เวลา VFS ต้องระบุ file system ของไฟล์อะไรก็จะมาดูใน Dentry นี้ก่อน ถ้าไม่เจอก็ค่อยไปไล่เช็ค mount table อีกทีแล้วเอาผลลัพธ์มาเก็บไว้ใน Dentry เพื่อใช้ในครั้งถัด ๆ ไป อีกทั้ง Dentry จะถูกเก็บเอาไว้ใน RAM 
เลยทำให้การเรียกใช้เร็วมาก ๆ ด้วย
</Note>

หลังจากเลือก driver ได้และส่งต่อ request ไปให้ driver แล้ว เราก็หมดธุระกับ layer นี้แล้วครับ
